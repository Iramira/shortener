# Сервис сокращения URL

HTTP-сервис сокращает ссылки, перенаправляет по ним и хранит историю для каждого пользователя. Данные и ключ подписи хранятся в памяти процесса: после перезапуска ссылки исчезают, а старые cookie перестают быть действительными.

## Запуск и тесты

Требуется Go 1.22 или новее: маршрутизация использует шаблоны методов и параметров в [`net/http.ServeMux`](https://go.dev/blog/routing-enhancements). Сторонних зависимостей нет. Выполняется из папки, где лежит `go.mod`:

```sh
go test ./...
go run ./cmd/shortener
```


Сервер слушает `http://localhost:8080`. Запросы к API можно отправлять из второго терминала.

## API

| Запрос | Успешный ответ | Другие предусмотренные ответы |
| --- | --- | --- |
| `POST /api/shorten` с JSON `{"url":"https://example.com/some/long/path"}` | `200`, JSON `{"result":"http://localhost:8080/abc123"}` | `400` для некорректного JSON или URL, `413` для тела больше 16 КиБ, `415` для явно указанного типа тела, отличного от `application/json` |
| `GET /{id}` | `307 Temporary Redirect` с исходным URL в `Location` | `404`, если ID неизвестен |
| `GET /api/user/urls` | `200`, JSON `[{"short_url":"http://localhost:8080/abc123","original_url":"https://example.com/some/long/path"}]` | `204`, если ссылок ещё нет; `401`, если cookie есть, но пуста или не имеет структуры `ID:подпись` |

На `POST /api/shorten` отсутствующая или недействительная cookie заменяется новой, и ссылка добавляется новому пользователю. На `GET /api/user/urls` отсутствие cookie или неверная подпись дают новую cookie и `204`; структурно некорректное значение даёт `401`. Для самого редиректа cookie не нужна: переход доступен любому, у кого есть короткая ссылка.
Для проверки истории (GET /api/user/urls) передайте cookie user_id, полученную при POST /api/shorten. Если при запросе истории cookie отсутствует или её подпись неверна, сервис выдаёт новую cookie и возвращает 204 No Content. Для перехода по короткой ссылке cookie не нужна.

## Устройство проекта

- `cmd/shortener` настраивает и запускает HTTP-сервер.
- `internal/app` регистрирует маршруты, проверяет входные данные и формирует ответы.
- `internal/auth` выдаёт `user_id` в формате `ID:подпись`, вычисляет HMAC-SHA256 и сравнивает подписи через `hmac.Equal`. Для локального HTTP у cookie нет флага `Secure`; включать его следует при использовании HTTPS. Cookie также имеет `HttpOnly`, `SameSite=Lax` и `Path=/`.
- `internal/storage` хранит два индекса под одним `sync.RWMutex`: по короткому ID для редиректа и по ID пользователя для истории. При совпадении короткого ID запись не перезаписывается, а хендлер генерирует другой ID.

HTTP-тесты на `httptest` проверяют сокращение, `307`, `404`, историю двух пользователей, выдачу и подмену cookie, `204`, `401` и некорректные запросы. Отдельные тесты проверяют HMAC по контрольному вектору и работу хранилища при конкуренции и коллизии.
